\begin{abstract}
This manuscript reports a software update of the Omnisolver
ecosystem~\cite{jalowiecki2021omnisolver}, introducing
\texttt{omnisolver-bruteforce}: a dedicated Omnisolver plugin that provides
exact exhaustive search for QUBO and Ising instances on CUDA-enabled GPUs, with
optional distributed execution across multiple GPUs and hosts via Ray. The
plugin builds on the single-GPU brute-force kernel
of~\cite{jalowiecki2021brute} and extends it in three ways: (i) integration as
a first-class plugin in the Omnisolver framework with a uniform Python and CLI
interface, (ii) distributed multi-GPU execution through a Ray-based
fixed-variable decomposition, and (iii) a stabilized \texttt{float32}
ground-state path that addresses the main practical pitfall of the original
implementation, namely numerical drift of incremental energy updates for
\(N \geq 40\). Stabilization combines compensated subtraction, periodic exact
energy re-anchoring, and best-buffer refresh, and is enabled automatically in
the affected regime; the public sampler API is unchanged. On dense random
Ising instances we measure exhaustive solve times up to \(N=58\) on
\(8\times\) NVIDIA H100 GPUs and project an \(N=60\) wall-clock of
\(\approx\!3\) days under the doubling rule \(t_{N+1}=2\,t_N\). The exhaustive
backend is positioned as a ground-truth oracle for benchmarking
state-of-the-art classical heuristics such as the Simulated Bifurcation
Machine~\cite{goto2016bifurcation,goto2019combinatorial,goto2021high}, which
recent comparative
studies~\cite{tuziemski2026limits,pawlowski2025closing} use to probe the
quantum--classical scaling gap.
\end{abstract}

\section{Motivation and significance}

Omnisolver~\cite{jalowiecki2021omnisolver} is a plugin-based framework that
provides a uniform Python and command-line interface to a range of Ising/QUBO
solvers, abstracting away their input/output conventions and integrating with
\texttt{dimod}. The original SoftwareX publication established the framework and
its first set of plugins (e.g.\ simulated annealing). The present paper is a
software update of that framework: it introduces and documents
\texttt{omnisolver-bruteforce}, a dedicated plugin that lifts a previously
stand-alone single-GPU exhaustive solver~\cite{jalowiecki2021brute} to a
first-class component of the Omnisolver ecosystem, adds distributed multi-GPU
execution, and stabilizes the numerical behavior of its fast ground-state path.

The role of an exhaustive solver in this ecosystem is to provide
\emph{certified} reference solutions for QUBO and Ising instances. Such
ground-truth answers are essential when benchmarking approximate or heuristic
methods, when verifying results from NISQ-oriented
workflows~\cite{preskill2018quantum}, and when assessing claims of quantum
runtime advantage. In particular, the Simulated Bifurcation Machine (SBM), a
classical heuristic based on simulating adiabatic bifurcations in a network of
nonlinear oscillators~\cite{goto2016bifurcation,goto2019combinatorial,
goto2021high}, has emerged as the state-of-the-art classical baseline for
dense QUBO/Ising problems. Recent comparative
studies~\cite{tuziemski2026limits,pawlowski2025closing} use the SBM to probe
the quantum--classical scaling gap and conclude that, on widely benchmarked
families of instances, the SBM matches or surpasses the scaling of current
quantum annealers. Such conclusions rely on knowing the true optimum on
representative instances --- which is precisely what an exhaustive GPU solver
delivers, up to the largest \(N\) that fits the compute budget.

The plugin builds on the CUDA brute-force kernel
of~\cite{jalowiecki2021brute}, which already demonstrated GPU-accelerated
exhaustive enumeration of spin configurations on a single device. The main
practical limitation of that implementation, when carried over to large dense
instances, is numerical drift in the fast ground-state mode
(\texttt{num\_states=1}): energies are tracked through long Gray-code chains
of incremental \texttt{float32} updates, and for \(N \geq 40\) the
accumulated rounding error becomes large enough to misrank the ground state in
adversarial cases. This is the central pitfall the update addresses, while
also packaging the kernel as a plugin and adding distributed orchestration.

The key update contributions are:
\begin{itemize}
    \item \textbf{First-class Omnisolver plugin.} The CUDA brute-force kernel
    is exposed through Omnisolver's plugin mechanism with a uniform Python and
    CLI interface, returning a \texttt{dimod.SampleSet} with runtime metadata.
    \item \textbf{Distributed multi-GPU execution.} A Ray-based controller
    splits a problem into \(2^k\) fixed-variable subproblems, dispatches them to
    GPU workers, and merges partial results, enabling exhaustive search at
    sizes previously out of reach for a single device.
    \item \textbf{Numerical stabilization of the fast ground-state path.}
    Compensated subtraction in incremental updates, periodic exact energy
    re-anchoring, and best-state buffer refresh after re-anchoring eliminate
    the \texttt{float32} drift observed for \(N \geq 40\); the stabilization is
    automatically enabled in the affected regime, with no API change.
    \item \textbf{Hardening for large state enumeration.} Kernel-step
    bookkeeping and 64-bit-safe bit operations support spin configurations of
    sizes well beyond the original single-GPU regime.
    \item \textbf{Extended validation.} Additional GPU tests cross-check
    energies against from-scratch exact recomputation and against
    \texttt{dimod.ExactSolver} on tractable instances; for our largest cases,
    we additionally verify that the SBM reaches the certified ground state
    (Section~\ref{sec:precision}).
\end{itemize}

\section{Software description}\label{sec:software-desc}

\subsection{Software architecture}
The plugin exposes two sampler classes:
\begin{itemize}
    \item \texttt{BruteforceGPUSampler}: single-node GPU exhaustive search.
    \item \texttt{DistributedBruteforceGPUSampler}: distributed exhaustive
    search over multiple GPUs and/or hosts via
    Ray~\cite{DBLP:journals/corr/abs-1712-05889}.
\end{itemize}

Performance-critical kernels are implemented in CUDA/C++, and exposed to Python
through a Cython wrapper. The plugin follows Omnisolver's plugin mechanism, so
users can call it from Python or from Omnisolver's CLI without custom glue code.

For distributed runs, the solver fixes \texttt{num\_fixed\_vars} variables and
enumerates all \(2^k\) fixed assignments. Each assignment defines a subproblem
with \(N-k\) unfixed variables solved by the GPU sampler. Ray schedules
subproblems across workers; partial results are gathered and merged on the
controller node. The workflow is shown in Fig.~\ref{fig:arch}.

\begin{figure}
    \includegraphics[width=\textwidth]{figs/omnisolver-distributed-diagram.pdf}
    \caption{ Distributed execution of \texttt{omnisolver-bruteforce}. The input
        BQM is partitioned into fixed-variable subproblems, dispatched to Ray
        workers, solved by GPU samplers, and merged into the final low-energy
        result. }
    \label{fig:arch}
\end{figure}

\subsection{Update-specific algorithmic changes}
The update focuses on the ground-only fast path (\texttt{num\_states=1}) in the
GPU backend. The previous implementation relied solely on incremental energy
differences along Gray-code steps. For \(N \geq 40\) in \texttt{float32}, this
could accumulate numerical error.

The updated backend introduces three stabilization mechanisms:
\begin{itemize}
    \item \textbf{Compensated subtraction} during incremental updates to reduce
    cancellation error.
    \item \textbf{Periodic re-anchoring}, i.e., recomputing exact energies from
    states at controlled intervals.
    \item \textbf{Best-buffer refresh} after re-anchoring, ensuring tracked
    minima remain consistent with recomputed energies.
\end{itemize}

In this branch, stabilization is automatically enabled for the large-\(N\)
\texttt{float32} ground-only configuration: \texttt{num\_states=1},
\texttt{dtype=float32}, \(N \geq 40\). No public method signature changed in
this update.

\subsection{Software functionalities}
Major plugin functionalities are:
\begin{itemize}
    \item exact exhaustive search for BINARY and SPIN BQMs (with internal
    vartype conversion),
    \item low-energy-spectrum mode (\texttt{num\_states>1}) and optimized
    ground-state mode (\texttt{num\_states=1}),
    \item distributed decomposition with Ray through \texttt{num\_fixed\_vars},
    \item Python API and Omnisolver CLI integration as the
    \texttt{bruteforce-gpu} solver,
    \item \texttt{dimod.SampleSet} output with runtime metadata (\texttt{solve\_time\_in\_seconds}).
\end{itemize}

\subsection{Validation in the update branch}
The update branch includes additional GPU tests for correctness of the
stabilized path. They verify that returned energies are consistent with CPU-side
exact energy evaluation and that ground-state results agree with
\texttt{dimod.ExactSolver} on tractable small instances. An opt-in performance
guard test is also included to ensure the stabilization path remains practical
in representative workloads.

\section{Illustrative examples}
The package is distributed as \texttt{omnisolver-bruteforce} on PyPI and can be
used stand-alone or through Omnisolver. Listing~\ref{lst:bf-code} shows an
example script that generates random instances and runs the distributed solver.

\begin{lstlisting}[language=Python,caption={Example distributed benchmark script for \texttt{omnisolver-bruteforce}},label={lst:bf-code}]
from omnisolver.bruteforce.gpu.distributed import DistributedBruteforceGPUSampler
from dimod.serialization import coo
from pathlib import Path
import numpy as np
import argparse
import json

RESULTS = Path("results")
INSTANCES = Path("instances")


class NpEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, np.integer):
            return int(obj)
        if isinstance(obj, np.floating):
            return float(obj)
        if isinstance(obj, np.ndarray):
            return obj.tolist()
        return super(NpEncoder, self).default(obj)


def generate(start, stop, step, skip_existing=True):
    INSTANCES.mkdir(parents=True, exist_ok=True)
    for d in range(start, stop + step, step):
        o_path = INSTANCES / f"{d}.txt"
        if skip_existing and o_path.is_file():
            continue
        J = 2 * (np.random.rand(d, d) - 0.5)
        with open(o_path, "w") as fd:
            for i in range(d):
                for j in range(i, d):
                    fd.write(f"{i} {j} {J[i, j]}\n")


def bench(start, stop, step, skip_existing=True):
    RESULTS.mkdir(parents=True, exist_ok=True)
    for d in range(start, stop + step, step):
        i_path = INSTANCES / f"{d}.txt"
        o_path = RESULTS / f"{d}.json"
        if not i_path.is_file():
            continue
        if skip_existing and o_path.is_file():
            continue
        with open(i_path) as fd:
            bqm = coo.load(fd, vartype="SPIN")
        sampler = DistributedBruteforceGPUSampler()
        result = sampler.sample(
            bqm,
            num_states=1,
            num_fixed_vars=3,
            suffix_size=23,
            grid_size=8192,
            block_size=1024,
            partial_diff_buffer_depth=10,
            num_steps_per_kernel=8192,
        )
        state = result.samples()[0, range(d)]
        result.info.update({"num_variables": d, "state": state, "energy": result.first.energy})
        with open(o_path, "w") as fd:
            json.dump(result.info, fd, indent=4, cls=NpEncoder)


def main():
    parser = argparse.ArgumentParser(
        description="Perform benchmark of distributed bruteforce solver from start to stop with step"
    )
    parser.add_argument("--start", type=int, default=60)
    parser.add_argument("--stop", type=int, default=40)
    parser.add_argument("--step", type=int, default=-2)
    parser.add_argument("--skip-existing", action="store_true")
    args = parser.parse_args()
    generate(args.start, args.stop, args.step, args.skip_existing)
    bench(args.start, args.stop, args.step, args.skip_existing)


if __name__ == "__main__":
    main()
\end{lstlisting}

# Run benchmark script from the project root

\end{lstlisting}

\subsection{Precision of the reported energies}
\label{sec:precision}
Because the GPU brute-force backend operates in \texttt{float32} for the
\texttt{num\_states=1} fast path, the energy returned by the sampler is subject
to incremental-update roundoff. To quantify this, we re-evaluate the energy of
each returned spin configuration from scratch in \texttt{float64} and compare
it to the value reported by the solver. For the two largest instances
(\(N=56,58\)), the absolute deviation between the reported and recomputed
energies is below \(2\times 10^{-6}\) on energies of magnitude
\(\mathcal{O}(10^{2})\), i.e. roughly eight significant digits, consistent with
the expected accuracy of stabilized \texttt{float32} accumulation. The same
recomputation is used to cross-check the SBM result on the same spin state:
the recomputed energies of the brute-force and SBM solutions agree to within
\(6\times 10^{-6}\), and the returned spin configurations are bit-identical
(Hamming distance \(0\)) at both \(N=56\) and \(N=58\). Thus, on these
instances the SBM does reach the ground state certified by exhaustive search,
and the residual discrepancies between the two reported energies are explained
entirely by single-precision roundoff rather than by either solver missing the
optimum.

\section{Impact}
This update contributes a production-ready exhaustive solver plugin inside the
Omnisolver ecosystem. It combines exactness guarantees with distributed GPU
execution, making it useful as a certification and benchmarking backend for
QUBO/Ising research pipelines.

The key practical outcomes are: (i) the CUDA brute-force kernel
of~\cite{jalowiecki2021brute} is now available as a uniform Omnisolver plugin,
removing the integration cost for downstream pipelines; (ii) distributed
multi-GPU execution extends the tractable problem size beyond the original
single-device regime; and (iii) the previously observed instability region for
large-\(N\) fast ground-state runs is closed, substantially improving the
reliability of exact-energy reporting in the very regime where exhaustive
verification is most computationally expensive.

On dense random Ising instances we measure exhaustive solve times up to
\(N=58\), reaching \(\approx\!67{,}900\) s (about 18.9 h) on \(8\times\)
NVIDIA H100 GPUs. The runtime curve is consistent with the expected
\(O(2^N)\) doubling per added spin, so under the empirical rule
\(t_{N+1}=2\,t_N\) an \(N=60\) instance is projected to take of the order of
\(\approx\!3\) days on the same hardware. This makes exhaustive verification
feasible at problem sizes that are well beyond single-device brute-force
baselines, and directly supports comparative studies of state-of-the-art
classical heuristics such as the SBM~\cite{tuziemski2026limits,
pawlowski2025closing}, where knowing the certified optimum on representative
instances is a prerequisite for meaningful scaling claims.

\section{Discussion and future extensions}
The update improves numerical robustness in the \texttt{num\_states=1} path,
but it does not change the exponential complexity of exhaustive search. In
practice, this solver remains most useful as a ground-truth backend for
benchmarking, debugging, and verification of approximate pipelines.

\subsection{Threats to validity}
The reported runtime envelope and numerical behavior depend on the hardware and
software stack, including GPU model, CUDA version, compiler flags, and Ray
runtime configuration. In particular, the projected \(N=60\) wall-clock of
\(\approx\!3\) days is an extrapolation from the measured \(N=58\) point under
the doubling rule and should be interpreted as a hardware-specific operating
point on \(8\times\)H100, not a universal runtime guarantee. Pre-asymptotic
deviations from exact doubling --- caused by kernel launch overhead, host/device
transfer, and Ray scheduling --- can shift the actual time at \(N=60\) by a
constant factor without changing the asymptotic \(O(2^N)\) scaling.

The stabilization path is validated in this update branch using representative
test instances and exact-energy cross-checks, but pathological coefficient
distributions can still stress \texttt{float32} arithmetic. For high-risk use
cases, users should validate with additional seeds and, where feasible, compare
against \texttt{float64} or exact small-scale baselines.

\subsection{When exhaustive bruteforce is not the right tool}
This solver is not intended for routine large-scale optimization where strict
latency constraints or limited GPU resources dominate. Because exhaustive search
scales exponentially, approximate or heuristic solvers are typically a better
primary method when the objective is fast near-optimal solutions for larger
instances.

In practical workflows, \texttt{omnisolver-bruteforce} is best used as a
calibration and certification backend: to validate solver quality on selected
instances, estimate optimality gaps, and debug model encodings.

A first extension path is broader precision policy control. The current
stabilization is automatically enabled for large-\(N\) \texttt{float32}
ground-only runs. Future versions can expose explicit user controls for
re-anchoring cadence and compensated-update modes, so users can tune stability
and runtime for specific hardware and instance families.

A second extension path is distributed post-processing. The present design
gathers subproblem results and merges them on the controller node. For very
large clusters, hierarchical merge strategies or tree reductions can reduce
controller bottlenecks and improve scalability.

A third extension path is stronger reproducibility packaging. Publishing a
versioned benchmark capsule with fixed seeds, hardware descriptors, and command
presets would make cross-platform validation of both runtime and numerical
behavior easier for the community.

\section{Conclusions}
We presented \texttt{omnisolver-bruteforce} as a software update to the
Omnisolver line of software~\cite{jalowiecki2021omnisolver}. The update
integrates the CUDA brute-force kernel of~\cite{jalowiecki2021brute} as a
first-class Omnisolver plugin, adds distributed multi-GPU execution through
Ray, and resolves the main numerical-stability limitation of the fast
ground-only GPU path for \(N \geq 40\), all without changing the public sampler
API. On dense random Ising instances we measure exhaustive solve times up to
\(N=58\) on \(8\times\)H100 and project an \(N=60\) wall-clock of
\(\approx\!3\) days under the empirical \(O(2^N)\) doubling rule. The plugin
thereby provides a practical exact-solver backend for QUBO/Ising benchmarking,
in particular as a ground-truth reference for state-of-the-art classical
heuristics such as the SBM~\cite{tuziemski2026limits,pawlowski2025closing}.
